Kafka 클러스터 관리자 사이트

3노드 KRaft 클러스터(SASL_SSL)를 감시하고 조치하는 사내 관리자 사이트. 기성 도구가 지원하지 않는 알림·인증서 만료 감시·복구 조치·승인 워크플로우를 직접 구현한다.

Spring Boot 4.1 · Java 21 Vue 3 + TypeScript kafka-clients 4.2.x H2 (파일 모드) Nginx + docker-compose

목적과 의도

Kafbat UI 같은 기성 도구를 쓰지 않고 전부 직접 개발한다. 실제로 필요한 기능 — 임계치 알림, 인증서 만료 감시, 반자동 복구 조치, 토픽 신청 워크플로우 — 이 기성 도구가 지원하지 않는 영역에 몰려 있기 때문이다.

ADMIN — 운영자

클러스터 모니터링, 장애 감지·알림 수신, 복구 조치 실행까지 전 권한. 오프셋 리셋·설정 변경 같은 위험 작업은 ADMIN만 가능하다.

DEVELOPER — 개발자

토픽/컨슈머 그룹 조회와 토픽 생성 신청까지. 조치 버튼은 화면에서 아예 보이지 않는다.

설계의 중심 규칙 — 안전장치

  • 위험 작업은 반드시 ops 모듈 경유. 컨트롤러가 kafka 모듈을 직접 호출해 조치하는 경로는 금지한다.
  • 실행 전 영향 요약 + 확인 절차, 실행 후 감사 로그(누가·언제·무엇을·결과)를 강제한다.
  • 자동 복구는 하지 않는다. 감지 → 알림 → 사람 확인 → 실행의 반자동 구조.

아키텍처

관리용 VM 1대에 컨테이너 2개(web, was)를 docker-compose로 배포한다. 브로커 장애 시 관리 도구가 함께 죽지 않도록 브로커 서버와 분리된 VM을 쓴다.

오프셋은 파티션 안의 일련번호(주소)라 파티션이 다르면 겹칠 수 있다. 값은 1,000자까지 표시.

순서 보장은 파티션 안에서만 성립한다 — 같은 키 ORD-8F2A1C의 CREATED(오프셋 1,204,329) → COMPLETED(1,204,330)가 같은 파티션 0에 순서대로 쌓인 것이 그 실례다. 같은 키는 항상 같은 파티션으로 가므로 "주문 하나 안의 순서"는 키만으로 보장되고, 다른 키(ORD-3B9D07, 파티션 2)와의 선후는 정의되지 않는다. 단, 파티션을 늘리면 키→파티션 매핑이 바뀌어 이 보장이 잠시 흔들린다 — 3단계 "파티션 증가" 조치에 경고를 붙이는 이유다.

랙(Lag) 이해하기

랙은 컨슈머가 아직 읽지 못하고 밀려 있는 메시지 수다.

랙 = 최신 오프셋 − 커밋 오프셋

  • 0 또는 일정 유지 — 정상. 소비가 생산을 따라잡는 중
  • 계속 증가 — 컨슈머 장애·처리 지연·트래픽 급증 신호
  • 특정 파티션만 증가 — 핫 파티션 또는 포이즌 메시지

해결은 컨슈머 애플리케이션의 몫이다: ① 다운스트림 배치화 등 처리 최적화 ② 컨슈머 스케일 아웃(파티션 수 한도) ③ 리밸런스·설정 튜닝 ④ 키 재설계·DLQ. 이 사이트는 감지·진단까지만 담당한다.
