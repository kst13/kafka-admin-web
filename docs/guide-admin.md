# kafka-admin 관리자(운영자) 가이드

Kafka 3노드 클러스터(KRaft, SASL_SSL)를 감시하고 조치하는 관리자 사이트의 **운영자(ADMIN)용** 안내서.
개발자용 개념·활용 안내는 [guide-developer.md](guide-developer.md), 화면을 직접 눌러보는 데모는 [guide.html](guide.html) 참고.

## 이 사이트의 목적

기성 도구(Kafbat UI 등)가 지원하지 않는 영역 — 임계치 알림, 인증서 만료 감시, 반자동 복구 조치, 승인 워크플로우 — 을 직접 구현한다. 운영자는 이 사이트로 **감지 → 알림 → 사람 확인 → 실행**의 반자동 장애 대응을 수행한다.

### 설계의 중심 규칙 (안전장치)

- 위험 작업은 **반드시 ops 모듈 경유** — 컨트롤러가 kafka 모듈을 직접 호출해 조치하는 경로 금지
- 실행 전 **영향 요약 + 확인 절차**, 실행 후 **감사 로그**(누가·언제·무엇을·결과) 강제
- **자동 복구 없음** — 최종 실행 판단은 항상 사람이 한다

## 배포 구성

```
관리용 VM (브로커와 분리 — 브로커 장애 시 관리 도구가 함께 죽지 않게)
├─ web: Nginx 컨테이너 — 정적 파일 서빙 + /api/* 리버스 프록시, 유일한 외부 노출(80/443)
└─ was: Spring Boot 컨테이너 — REST API, 60초 수집 스케줄러, H2(파일 모드, 볼륨 마운트)
        └─ SASL_SSL :9094 → 브로커 3대 (전용 admin SCRAM 계정 + truststore)
```

- 방화벽: WAS → 브로커 **3대 전부** TCP 9094 개방 (bootstrap 이후 각 브로커에 직접 접속하므로 1대만 열면 안 됨)
- 외부 모니터링 스택 없이 앱 내 스케줄러로 수집 — 앱이 죽으면 수집도 죽는 약점은 단순함을 우선해 수용
- 시크릿(SCRAM 비밀번호, truststore 비밀번호)은 env/마운트 파일로 주입, 코드·이미지에 포함 금지

### 실행

```bash
# 배포
cd deploy && cp .env.example .env   # 값을 채운다
docker compose up -d --build
```

최초 기동 시 사용자가 0명이면 `admin` 계정이 `$ADMIN_INITIAL_PASSWORD` 값으로 생성된다.

## 감시 체계 (2단계 완료)

| 항목 | 내용 |
|---|---|
| 수집 주기 | 60초 — 그룹별 랙·소비량(전체/토픽별), URP, 브로커별 디스크 사용률, 브로커 수 |
| 이력 보존 | H2에 7일 (매일 03시 정리) |
| 알림 | 임계치 초과 시 이력 기록, 같은 (유형, 대상)은 30분 쿨다운으로 중복 억제 |
| 수집 실패 | **3회 연속 실패 자체가 알림** — 클러스터 전면 장애 신호 |
| 인증서 | 매일 03시(KST) + **기동 직후 1회** TLS 인증서 만료 점검, D-30 이내면 경고 |
| 기본 임계치 | 랙 1,000 / 디스크 80% / 인증서 D-30 (env로 재정의: `MONITOR_*`) |

발송 채널(웹훅 등) 연결은 3단계. 현재는 알림 화면에서 이력으로 확인한다.

## 화면 읽는 법 (운영 관점)

### 클러스터 화면

- **브로커 표**: 3대가 다 보이는지, 컨트롤러가 누구인지. 브로커 무응답이면 사이트는 살아 있고 "브로커 접속 불가"로 표시된다(5초 타임아웃).
- **감시 상태**: 마지막 수집 시각과 연속 실패 횟수. 연속 실패가 보이면 브로커/네트워크부터 의심.
- **인증서 표**: 브로커별 만료일과 D-day. D-30 이하는 빨간색 — 인증서 갱신 작업을 계획한다.
- **URP 추이**: 0이 정상. 0보다 크면 어느 브로커의 복제가 뒤처졌다는 뜻 — 지속되면 브로커 장애/디스크·네트워크 저하를 조사한다.
- **디스크 사용량 + 추이**: 브로커별 사용률과 24시간 추이. 임계(80%) 초과 시 알림. **"지금 81%"보다 "어제부터 급증했나"가 판단 기준** — 추이가 급증이면 retention 축소(3단계 조치)가 응급 대응이다.

### 알림 화면

최근 이력 50건. 유형별 대응:

| 유형 | 의미 | 1차 대응 |
|---|---|---|
| LAG | 그룹 랙 임계 초과 | 그룹 상세에서 파티션별 분포·멤버 확인 → 컨슈머 앱 팀에 전달 (해소는 앱의 몫) |
| URP | 미복제 파티션 발생 | 브로커 생존/디스크/네트워크 확인 → 복구 후 따라잡기 복제 대기 |
| DISK_USED_PCT | 디스크 임계 초과 | 추이 확인 → 원인 토픽 파악 → retention 축소 검토 |
| CERT_EXPIRY | 인증서 D-30 이내 | 인증서 갱신 일정 수립 |
| COLLECTOR_FAILURE | 수집 3연속 실패 | 전면 장애 신호 — 브로커 클러스터 상태 최우선 확인 |

## 운영자가 알아야 할 핵심 개념

### 리더 · 레플리카 · ISR · URP

- 파티션마다 사본(레플리카)이 RF개 있고, 그중 **1벌만 리더**(읽기/쓰기 담당), 나머지는 팔로워(복제만).
- **ISR** = 리더와 동기화가 살아 있는 레플리카 명단. 장애 시 새 리더는 **ISR 안에서만** 선출되므로 데이터가 유실되지 않는다.
- **URP** = ISR < 레플리카인 파티션 수. 평상시 0, 0이 아니면 여유분이 깎인 상태(한 대 더 죽으면 위험)라는 조기 경보.

### 표준 설정 관례 (3노드 기준)

- **RF=3 + `min.insync.replicas=2` + 프로듀서 `acks=all`** — 1대 장애(롤링 재시작 포함)에도 쓰기 지속·무유실. RF=2는 1대 장애 순간 위험 상태가 되므로 운영 토픽에 비권장.
- 파티션 수는 **3의 배수**(리더 균등 분배). 일반 토픽 6~12로 시작, 랙이 스케일 아웃으로 안 잡힐 때 증설. 파티션은 **줄일 수 없다.**

## 3단계 조치 목록 (예정) — 어떤 장애에 어떤 조치인가

| 조치 | 사용 상황 | 주의 |
|---|---|---|
| retention 변경 | 디스크 급증 응급 대응 (보존 7일→1일 등) | — |
| 파티션 증가 | 컨슈머 병렬성 한계로 랙 지속 | 감소 불가, 키→파티션 매핑 변경 |
| preferred 리더 선출 | 재시작 후 리더 쏠림 해소 | 데이터 이동 없음, 안전 |
| 오프셋 리셋 | 밀린 메시지 건너뛰기/되감기 (최후 수단) | **데이터 건너뜀**, 활성 그룹 불가 → 컨슈머 먼저 중지 |
| unclean 리더 선출 | ISR 전멸 시 가용성 우선 복구 | **데이터 유실 감수** — 2차 확인 절차 |
| 파티션 재할당 | 브로커 교체, 디스크 불균형, RF 변경 | 복제 트래픽 발생 |
| 복제 스로틀 | 재할당·복구 복제가 서비스 트래픽 침해 시 | 걸기/풀기 한 쌍 |

연결해서 보면: **URP 알림** → 브로커 복구 → (필요 시 스로틀) → 리더 쏠림 남으면 preferred 선출.
**랙 알림** → 앱 쪽 해결 우선 → 안 되면 파티션 증가 → 최후에 오프셋 리셋.
**디스크 알림** → retention 축소.

## 사이트가 해줄 수 없는 것 (기대치 관리)

- **랙 해소** — 컨슈머 애플리케이션의 처리 능력 문제. 사이트는 감지·진단 정보 제공까지. ([개발자 가이드](guide-developer.md)의 랙 해소 절 참고)
- 활성 그룹의 오프셋 리셋 — Kafka 프로토콜 제약. 그룹 정지 안내를 UI에 표시.
- 메시지 본문이 화면에 노출되므로(토픽 상세 최근 메시지), 개인정보가 담긴 토픽이 있다면 노출 정책을 검토할 것.
