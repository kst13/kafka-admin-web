# kafka-admin 개발자 가이드

Kafka 관리자 사이트의 **개발자(DEVELOPER)용** 안내서 — 화면 활용법과 그 바탕이 되는 Kafka 핵심 개념.
운영·조치·배포 관점은 [guide-admin.md](guide-admin.md), 화면을 직접 눌러보는 데모는 [guide.html](guide.html) 참고.

## 개발자가 이 사이트에서 할 수 있는 것

DEVELOPER 역할은 **조회 전용**이다 (조치 버튼은 화면에 표시되지 않음).

| 하고 싶은 것 | 화면 |
|---|---|
| 내 메시지가 실제로 발행됐는지, 포맷이 맞는지 | 토픽 상세 → **최근 메시지** (키·값·오프셋, 최신순 50건 · 값은 1,000자까지 표시) |
| 내 컨슈머가 잘 소비하고 있는지 | 그룹 상세 → 총 랙, **최근 소비 내역**(언제 어느 토픽에서 몇 건) |
| 소비가 밀리는지, 언제부터인지 | 그룹 상세 → 랙 추이 차트, 시간대별 소비량 |
| 어느 인스턴스가 어느 파티션을 잡았는지 | 그룹 상세 → **멤버** 표 (리밸런스·쏠림 진단) |
| 토픽 구성·설정 확인 | 토픽 상세 → 파티션/ISR, retention 등 설정 |

토픽 생성 신청 워크플로우는 4단계 예정. 그 전까지는 토픽 생성과 **컨슈머 그룹 사전 등록**(앱 배포 전에 group.id 와 시작 위치를 미리 잡아두는 것)을 운영자에게 요청한다.

## 핵심 개념 1 — 토픽 · 파티션 · 오프셋

- **토픽**은 논리적 이름, 실제 데이터는 **파티션**(병렬 처리 단위)에 나뉘어 저장된다.
- **오프셋**은 파티션 안에서 메시지마다 붙는 일련번호(주소)다. 0부터 증가하고 재사용되지 않으며, **소비해도 사라지지 않는다** — 컨슈머가 읽는다는 건 "여기까지 읽었다"는 책갈피(커밋 오프셋)를 옮기는 것뿐이다.
- 오프셋은 **파티션별로 따로** 센다. 파티션 0의 오프셋 5와 파티션 1의 오프셋 5는 다른 메시지다.
- **건수는 항상 오프셋 두 개의 차이**다: 랙 = 최신 오프셋 − 커밋 오프셋, 소비량 = 커밋 오프셋의 증가분. (트랜잭션 마커·압축 때문에 1~2건 오차가 있을 수 있는 근사치 — 추세를 보는 지표다)

## 핵심 개념 2 — 랙(Lag)

**컨슈머가 아직 읽지 못하고 밀려 있는 메시지 수.** `랙 = 최신 오프셋 − 커밋 오프셋`

- **0 또는 일정 수준 유지** → 정상 (소비가 생산을 따라잡는 중)
- **계속 증가** → 컨슈머 장애·처리 지연·트래픽 급증 신호
- **특정 파티션만 증가** → 핫 파티션(키 쏠림) 또는 포이즌 메시지 — 그룹 상세의 파티션별 분포와 멤버 표로 원인 인스턴스를 좁힌다

### 랙 해소는 애플리케이션의 몫이다 (우선순위 순)

사이트는 감지·진단까지만 담당한다. 해소는:

1. **처리 로직 최적화** — 랙의 원인은 대부분 다운스트림(DB·외부 API). 건별 처리를 poll 배치 단위 **bulk 처리**로 바꾸는 것이 효과가 가장 크다.
2. **컨슈머 스케일 아웃** — 같은 그룹에 인스턴스 추가. 단 **컨슈머 수 ≤ 파티션 수** (초과분은 논다).
3. **리밸런스·설정 튜닝** — 배치 처리 시간에 맞춰 `max.poll.interval.ms` 상향(짧으면 리밸런스 루프로 악화), `CooperativeStickyAssignor`·정적 멤버십(`group.instance.id`)으로 리밸런스 중단 최소화.
4. **키 설계·포이즌 메시지** — 핫 파티션은 파티션 키 재설계, 처리 실패 메시지는 재시도 제한 + **DLQ 토픽**으로 격리 (1건이 파티션 전체를 멈추게 하지 않기).

오프셋 리셋은 밀린 메시지를 처리하는 게 아니라 **건너뛰거나 되감는** 최후 수단이다 (운영자 조치, 3단계).

## 핵심 개념 3 — 컨슈머 그룹 · 멤버 · 담당 파티션

- **그룹**이 지속적인 구독자(팀)다. 커밋 오프셋·랙·상태의 주인은 그룹이며, `__consumer_offsets`에 (그룹, 토픽, 파티션) 단위로 저장된다.
- **멤버**는 지금 접속해 있는 컨슈머 인스턴스(팀원)다. 재시작·리밸런스마다 바뀌는 일시적 존재라서, 멤버가 죽어도 그룹의 책갈피에서 다른 멤버가 이어 읽는다 — 이게 컨슈머 쪽 장애 복구다.
- **담당 파티션**은 그룹 안의 배타적 업무 분담표다. 같은 그룹 안에서 **한 파티션은 한 멤버만** 읽는다 (중복 처리 방지 + 순서 보장). 멤버별 담당은 일부씩이지만 **합치면 전체** — "전부 받는" 주체는 그룹이다. 문제 신호는 담당이 나뉜 것이 아니라 어느 멤버의 담당에도 없는 파티션이 생기는 것.

### 그룹 ID 규칙 — 실수하기 쉬운 곳

`group.id`는 그냥 문자열 약속이고 Kafka는 충돌을 막지 않는다.

| 요구 | 그룹 ID | 결과 |
|---|---|---|
| 같은 앱을 여러 대로 확장 | **같게** | 파티션 분담 = 병렬 처리 (정상) |
| 다른 앱이 각자 전체 데이터 필요 | **다르게** | 각자 전체 스트림 수신 (팬아웃 — 그룹마다 책갈피 독립) |
| 다른 앱이 같은 그룹 ID (사고) | 같게 | **메시지가 앱들 사이에 쪼개짐** — "절반만 온다" 장애 |

그룹 ID는 서비스 이름 기준으로 짓는다 (`order-settlement`, `order-statistics`). 그룹 상세 멤버 표에 클라이언트 ID·호스트 패턴이 다른 멤버가 섞여 있으면 그룹 ID 충돌을 의심할 것.

## 핵심 개념 4 — 순서 보장

**Kafka의 순서 보장 = 파티션 안의 오프셋 순서.** 토픽 전체 순서는 보장되지 않는다.

- **같은 키는 항상 같은 파티션**으로 가므로, 순서가 필요한 단위(예: 주문 ID)를 키로 잡으면 그 단위의 순서가 보장된다. 예: 키 `ORD-...`의 CREATED → COMPLETED는 같은 파티션에 순서대로 쌓인다. 다른 주문끼리의 선후는 정의되지 않는다 — 대부분 그걸로 충분하다.
- 끝에서 끝까지 순서가 유지되는 경로: **멱등 프로듀서(`enable.idempotence=true`, 최신 기본값) + 같은 키 + 파티션당 단일 스레드 처리.**
- 순서가 깨지는 흔한 지점:
  - 프로듀서 재시도 (멱등성 없이 `max.in.flight` > 1)
  - **컨슈머 내부 스레드 풀 병렬 처리** — 랙 해소와 순서의 트레이드오프
  - DLQ 재처리 (원래 순서에서 이탈)
  - **파티션 증가** — 키→파티션 매핑이 바뀌어 같은 키가 잠시 두 파티션에 걸침
- 전역 순서가 꼭 필요하면 파티션 1개(병렬성 포기). 실무에선 "키 범위 순서면 충분한가"를 먼저 검토한다.

## 토픽을 새로 설계할 때

- **파티션 수**: 목표 처리량 ÷ 컨슈머 1개 처리 속도 + 성장 여유. 3노드 관례는 3의 배수, 일반 토픽 6~12로 시작. 파티션은 늘릴 수만 있고 **줄일 수 없으며**, 늘리면 키 순서 보장이 흔들리므로 순서가 중요한 토픽은 처음부터 여유 있게.
- **복제 팩터**: 운영 토픽은 3 고정 (`min.insync.replicas=2`, `acks=all`과 세트).
- **키**: "순서·집계가 필요한 단위"로 정한다. 특정 키로 트래픽이 쏠리면(대형 고객 등) 핫 파티션이 되므로 분포도 고려.
- **명명**: 그룹 ID·토픽 이름은 서비스 기준으로 명확하게.

## 로컬 개발

```bash
# 백엔드 (PLAINTEXT 로컬 브로커 기준)
cd was
ADMIN_INITIAL_PASSWORD=devpw KAFKA_BOOTSTRAP_SERVERS=localhost:9092 \
KAFKA_SECURITY_PROTOCOL=PLAINTEXT ./gradlew bootRun

# 프론트
cd web && npm run dev
```

- 브로커가 없어도 사이트는 뜬다 — 조회 화면이 "브로커 접속 불가"(503)로 표시될 뿐이다.
- 토픽 상세의 "최근 메시지"는 그룹 없이(assign+seek) 읽는 순수 조회라 **기존 컨슈머 그룹의 오프셋·랙에 영향을 주지 않는다.** 안심하고 사용할 것.
